# 🚌 Lviv Controllers Map: план проєкту

Live-карта Львова, де на актуальних маршрутах автобусів у реальному часі відображаються контролери, витягнуті з повідомлень Telegram-каналу і прив'язані до конкретного борту.

---

## 1. Мета і принципи

**Мета:** за 5 секунд відповісти на питання «де зараз контролери і в якому автобусі?».

**Принципи:**
- **Real-time за замовчуванням.** Нові повідомлення з'являються на карті без перезавантаження (SSE/WebSocket).
- **Свіжість важливіша за повноту.** Кожна мітка має вік, рівень довіри і автоматично згасає.
- **Деградація без падіння.** Якщо live-GPS недоступний, показуємо мітку на зупинці/вулиці. Якщо LLM впала, працює парсер на правилах.
- **Спочатку MVP без складного.** Прив'язку до борту додаємо після того, як працює парсинг.

## 2. Архітектура

```
┌──────────────┐   нові повідомлення   ┌──────────────┐
│ Telegram     │ ────────────────────▶ │ Ingestor     │
│ канал        │   (Telethon, events)  │ (listener)   │
└──────────────┘                       └──────┬───────┘
                                              ▼
                                       ┌──────────────┐
                                       │ Parser       │  LLM + правила
                                       │ (NLP → JSON) │
                                       └──────┬───────┘
                                              ▼
┌──────────────┐   позиції бортів      ┌──────────────┐     ┌────────────┐
│ GPS-джерело  │ ────────────────────▶ │ Matcher      │ ◀── │ Stops /    │
│ (EasyWay/    │   (polling 5-10 с)    │ (snap to bus)│     │ Routes DB  │
│  GTFS-RT)    │                       └──────┬───────┘     └────────────┘
└──────────────┘                              ▼
                                       ┌──────────────┐
                                       │ State store  │  активні мітки + TTL
                                       │ (Redis/mem)  │
                                       └──────┬───────┘
                                              ▼
                                       ┌──────────────┐   SSE / WS   ┌─────────┐
                                       │ API (FastAPI)│ ───────────▶ │ Web map │
                                       └──────────────┘              │ MapLibre│
                                                                     └─────────┘
```

**Стек (рекомендований):**

| Шар | Вибір | Чому |
|---|---|---|
| Backend | Python 3.12 + FastAPI | швидко, async, зручно з Telethon |
| Telegram | Telethon | читає публічні канали без адмінства, події в реальному часі |
| БД | PostgreSQL + PostGIS (або SQLite + SpatiaLite для старту) | геозапити «найближчий автобус до точки» |
| Стан | Redis (або in-memory dict на MVP) | TTL міток, pub/sub для стріму |
| Парсинг | LLM зі structured output + fallback на regex | вільний текст з помилками |
| Фронт | MapLibre GL JS + vanilla/Svelte/React | WebGL, плавна анімація, безкоштовно |
| Реалтайм | Server-Sent Events | простіше за WebSocket, достатньо для односторонніх оновлень |
| Деплой | Docker Compose на VPS / Fly.io / Railway | дешево, один контейнер на сервіс |

## 3. Джерела даних (вирішити першим!)

Це найбільший ризик проєкту. Перш ніж писати код, потрібно з'ясувати, звідки брати live-позиції.

### 3.1 Статика: маршрути й зупинки
Варіанти за пріоритетом:
1. **GTFS Львова**, якщо є відкритий фід (перевір портал відкритих даних міста та Transitland / Mobility Database).
2. **OpenStreetMap** через Overpass API: маршрути (`relation[route=bus]`) і зупинки (`highway=bus_stop`). Безкоштовно, легально, завжди під рукою. Якість у Львові зазвичай непогана, але треба перевірити.
3. Власний експорт з EasyWay, якщо дозволяють умови.

### 3.2 Live-позиції автобусів
- Станом на пошук: у відкритих матеріалах EasyWay згадується, що GPS-дані Львова належать приватній компанії (SoftServe), а не міській владі, тобто офіційного відкритого GTFS-Realtime може не бути. **Актуальність цього треба перевірити особисто**, бо інформація могла змінитися.
- **Що зробити:**
  - [ ] Перевірити, чи є публічний API/GTFS-RT у EasyWay або міського оператора.
  - [ ] Написати на пошту EasyWay/міському департаменту транспорту про легальний доступ (для некомерційного сайд-проєкту часто погоджуються).
  - [ ] Прочитати ToS: неофіційний скрейпінг може порушувати правила.
- **План Б (якщо live-GPS недоступний):** показувати мітки на **зупинках/відрізках маршруту** без прив'язки до борту, плюс розклад/інтервал як оцінку. Продукт все одно корисний.

### 3.3 Telegram
- Читати публічний канал через **Telethon** (user-session) із `events.NewMessage` для миттєвих подій.
- При старті один раз підтягнути історію за останні 60 хв.
- Не пересилай і не публікуй чужий текст повністю: показуй структуровані дані + посилання на оригінальне повідомлення. Варто повідомити автору каналу про проєкт.

## 5. Парсинг повідомлень (серце проєкту)

### 5.1 Типи повідомлень, які треба розпізнавати
| Тип | Приклад | Дія |
|---|---|---|
| Нова поява | «Контролери в 5А на Стрийській, їдуть в центр» | створити sighting |
| Рух | «Вийшли на Двірці, пішли в 30» | оновити/створити нову мітку |
| Зняття | «В 5А чисто», «вже вийшли» | позначити `cleared` |
| Сміття | жарти, питання, реклама | ігнорувати |

### 5.2 Двоступеневий підхід
1. **LLM-екстрактор** зі строгою JSON-схемою. Зміст prompt: список відомих маршрутів і зупинок як словник, правила «не вигадуй», вихід тільки JSON.
   ```json
   {
     "type": "sighting | cleared | noise",
     "routes": ["5А"],
     "location_text": "Стрийська",
     "direction_hint": "центр",
     "relative_time_min": 0,
     "confidence": 0.8
   }
   ```
2. **Правила як страховка:** regex на номери маршрутів (`\b\d{1,2}\s?[А-Яа-яA-Za-z]?\b`), ключові слова («чисто», «вийшли»), fuzzy-match назв зупинок (RapidFuzz, нормалізація: регістр, апострофи, «вул.», російські/українські варіанти).

### 5.3 Геокодування місця
`location_text` → зупинка (fuzzy по `stops.name` і `name_aliases`) → якщо не знайшли, по вулиці з OSM/Nominatim (кешувати результат). Для неоднозначності брати зупинку на маршруті, який згаданий у повідомленні.

### 5.4 Якість і оцінка
- Зібрати **золотий датасет**: ~200 реальних повідомлень, розмічених руками.
- Метрики: точність маршруту, точність зупинки, % шуму. Ціль для MVP: ≥85% по маршруту.
- Зберігати `raw_text` + результат парсера, щоб перепарсити після покращень.

## 6. Прив'язка контролерів до конкретного автобуса (Matcher)

Задача: за `(маршрут, зупинка, напрямок, час події)` знайти борт.

**Алгоритм:**
1. Визначити `direction_id` з `direction_hint` (порівняти з кінцевими маршруту або з порядком зупинок).
2. З історії позицій узяти борти цього маршруту й напрямку **на момент `seen_at`** (а не зараз!): повідомлення запізнюється на 1-3 хв.
3. Вибрати борт із мінімальною відстанню вздовж лінії маршруту до зупинки (не по прямій, а по геометрії).
4. Порахувати `confidence`: чим менша відстань і чим менше кандидатів поруч, тим вище.
5. Якщо кандидатів кілька з однаковою вірогідністю, показати мітку на відрізку маршруту (діапазон), а не на конкретному борту.
6. Після прив'язки мітка **їде разом з автобусом** (оновлюється з його позицією).

**Правила життя мітки:**
- Початок: `confidence` з парсера × з матчера.
- Згасання: лінійно за 15 хв (прозорість → 0), потім `expired`.
- Зняття: повідомлення «чисто» або голоси користувачів.
- Якщо автобус завершив рейс або зник з GPS, мітка переходить у стан «остання відома позиція».

## 7. Інтерактивність і «актуальність»

**Реалтайм-канал:** `GET /stream` (SSE) віддає події `sighting_created`, `sighting_updated`, `vehicle_batch` (позиції пачкою раз на 5-10 с), `sighting_expired`.

**Фронтенд:**
- Базова карта Львова (MapLibre + OSM-тайли/векторні тайли).
- Лінії маршрутів із кольорами, вмикання/вимикання окремих маршрутів.
- Автобуси як стрілочки з плавною інтерполяцією між оновленнями.
- Мітки контролерів: колір за свіжістю (🔴 <3 хв, 🟠 3-8 хв, 🟡 8-15 хв), підпис «5 хв тому».
- Клік на мітку: текст оригінального повідомлення (коротко), маршрут, напрямок, довіра.
- Кнопки **«Ще тут» / «Вже нема»**: краудсорс-підтвердження, що продовжує/гасить мітку (з анонімним rate-limit по IP/fingerprint).
- Фільтр «мій маршрут» (запам'ятовується в localStorage).
- Режим «поруч зі мною» (геолокація у браузері, тільки на клієнті).
- PWA: установка на телефон, швидкий старт.
- Push-сповіщення: «контролери на вашому маршруті» (Web Push, на пізніше).
- Тема світла/темна, мобільний UI першим.

## 8. Фази та терміни

Орієнтовно 1-2 години вечора щодня.

### Фаза 0. Розвідка (1-2 дні)
- [ ] З'ясувати джерело live-GPS і легальність.
- [ ] Знайти/зібрати статичні дані маршрутів і зупинок (GTFS або OSM).
- [ ] Зібрати ~200 повідомлень каналу для тестів.

### Фаза 1. Ingest + парсинг (3-5 днів)
- [ ] Telethon-слухач, збереження в БД, історія за останню годину.
- [ ] Парсер: правила + LLM, золотий датасет, метрики.
- [ ] Матчинг зупинок (fuzzy) і геокодування.

### Фаза 2. MVP-карта без live-автобусів (3-4 дні)
- [ ] FastAPI + SSE.
- [ ] MapLibre: маршрути, зупинки, мітки з таймером та згасанням.
- [ ] Деплой, публічне посилання. **Це вже корисний продукт.**

### Фаза 3. Live-автобуси і прив'язка (5-7 днів)
- [ ] Поллер позицій, історія позицій (зберігати хоча б 30 хв).
- [ ] Matcher, мітки їдуть разом з автобусом.
- [ ] Інтерполяція руху на фронті.

### Фаза 4. Інтерактив і довіра (3-5 днів)
- [ ] «Ще тут» / «Вже нема», фільтри, «поруч зі мною».
- [ ] PWA, push-сповіщення.
- [ ] Метрики якості в проді (скільки міток підтверджено/спростовано).

### Фаза 5. Полірування
- [ ] Спостереження за навантаженням, кешування, логи, алерти на падіння слухача.
- [ ] Сторінка «Про проєкт», атрибуція джерел, політика приватності.

## 9. Ризики та пом'якшення

| Ризик | Імовірність | Що робити |
|---|---|---|
| Немає легального доступу до live-GPS | висока | план Б: мітки на зупинках/відрізках; запит на офіційний доступ |
| Парсинг помиляється з маршрутом | середня | золотий датасет, показ `confidence`, «Вже нема» від юзерів |
| Затримка повідомлень → неправильний борт | висока | матчити на `seen_at`, показувати діапазон при невпевненості |
| Telegram блокує сесію / flood limits | низька | один клієнт, обробка `FloodWait`, не пулити історію часто |
| Вартість LLM | низька | короткі повідомлення, кеш, дешева модель, правила для простих випадків |
| Претензії щодо контенту/даних | середня | посилання на джерело, без копіювання тексту, зв'язок з автором каналу |
| Хибні/зловмисні повідомлення | середня | rate-limit голосування, довіра до джерела = один канал |

## 10. Корисні нюанси

- **Час:** усе зберігати в UTC, показувати Europe/Kyiv.
- **Правки повідомлень:** слухати `MessageEdited`, адміни часто виправляють текст.
- **Антиспам навантаження:** не опитувати GPS частіше ніж раз на 5-10 с, віддавати клієнтам один спільний кеш.
- **Тестування парсера:** фіксувати кожну помилку з прод як новий тест-кейс.
- **Етика:** проєкт про інформування пасажирів, а не про переслідування працівників. Не показуй особисті дані, фото чи імена.
